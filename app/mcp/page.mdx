# MCP server

day3 runs a Model Context Protocol server, so an AI editor can work with your
campaigns and automations directly. Drafts land as **editable composer blocks**,
not opaque HTML, so you can still edit them by hand.

```
https://go.day3.app/api/mcp
```

One HTTP endpoint, authenticated with your [API key](/authentication). Nothing to
install, nothing to run locally.

## Setup

Every editor does the same thing: point at the URL, send the key as a header.

<Tabs items={["Claude Code", "Cursor", "VS Code"]}>
<Tabs.Tab>

Run this in your project, then ask Claude to write you an email.

```bash
claude mcp add --transport http day3 https://go.day3.app/api/mcp --header "Authorization: Bearer $DAY3_API_KEY"
```

<Callout type="warning">
Keep it on **one line**. A `\` continuation is bash only; on Windows the
`--header` line runs as its own command and never arrives. The server is then
added without a key, returns 401, and the client reports
`Invalid OAuth error response: Unrecognized token '<'`, which says nothing about
the missing header.
</Callout>

</Tabs.Tab>
<Tabs.Tab>

Add to `.cursor/mcp.json` in your project, or `~/.cursor/mcp.json` for all
projects.

```json
{
  "mcpServers": {
    "day3": {
      "url": "https://go.day3.app/api/mcp",
      "headers": { "Authorization": "Bearer day3_live_xxxxxxxxxxxxxxxxxxxx" }
    }
  }
}
```

</Tabs.Tab>
<Tabs.Tab>

Add to `.vscode/mcp.json`. The input prompt keeps the key out of a file that
usually gets committed.

```json
{
  "inputs": [
    {
      "type": "promptString",
      "id": "day3-key",
      "description": "day3 API key",
      "password": true
    }
  ],
  "servers": {
    "day3": {
      "type": "http",
      "url": "https://go.day3.app/api/mcp",
      "headers": { "Authorization": "Bearer ${input:day3-key}" }
    }
  }
}
```

## Tools

| Tool | What it does |
| --- | --- |
| `day3_context` | Account context: audiences, senders, plan state. Call this first. |
| `day3_list_campaigns` | List campaigns. |
| `day3_get_campaign` | Read one campaign, including its body. |
| `day3_create_campaign` | Create a draft. |
| `day3_update_campaign` | Edit a draft. |
| `day3_preview_campaign` | Render it, with theme, merge tags and footer applied. |
| `day3_send_test` | Send to addresses the caller names. Never the audience. |
| `day3_send_campaign` | Send to the whole audience. Needs `campaigns:send`. |
| `day3_schedule_campaign` | Schedule a send. Needs `campaigns:send`. |
| `day3_list_automations` | List [automations](/automations), with status and trigger. |
| `day3_enroll_in_automation` | Put one person into a flow. Needs `automations:enroll`. |

## Sending is off by default

`day3_send_campaign` and `day3_schedule_campaign` need the `campaigns:send`
scope. `day3_enroll_in_automation` needs `automations:enroll`. Both are off
unless you enabled them when minting the key.

A script does what its author wrote. An agent decides for itself, and "email
everyone on the list" is not a decision to hand over by default. Enrolling
promises a stranger every email in a flow, so it is scoped too. Listing
automations names flows, not people, and is not.

`day3_send_test` needs **no scope**. It only reaches addresses the caller names,
and it is capped and rate-limited. The default key gives your assistant the full
draft, preview, test loop and stops at the audience.

Want an agent to send? Mint a second key with the scope on. Scopes cannot be
added to an existing key, so the grant stays visible in your key list.

## A typical session

> Read our last three campaigns, then draft an August release note in the same
> voice. Cover sending domains and the new API. Preview it and send me a test.

The assistant calls `day3_context` for your audience and sender,
`day3_list_campaigns` and `day3_get_campaign` to learn the voice,
`day3_create_campaign` to write the draft in
[day3 Markdown](/campaigns#day3-markdown), `day3_preview_campaign` to check it,
and `day3_send_test` to put it in your inbox.

The draft waits in day3 as real composer blocks. Nothing has reached your list.

## Keep the key out of prompts

Prompts get copied into chat tools, issue trackers and logs. Set `DAY3_API_KEY`
in your environment and let the editor config read it, as in the Claude Code and
VS Code examples. When an assistant calls the REST API directly, tell it to read
the key from the environment.
